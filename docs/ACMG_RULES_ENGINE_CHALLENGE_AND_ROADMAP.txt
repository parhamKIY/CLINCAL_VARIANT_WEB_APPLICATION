ACMG/AMP RULES ENGINE: CHALLENGE, EVIDENCE GAPS, AND ROADMAP
================================================================

Document status: Planning proposal only
Implementation status: Not started
Scope: Germline Mendelian sequence variants


1. PURPOSE
----------

The application currently accepts a small set of variants and enriches them
with annotation, population, clinical, gene-disease, and phenotype evidence.
The proposed next capability is a deterministic ACMG/AMP rules engine that:

1. evaluates the evidence available for each variant;
2. records which ACMG/AMP criteria are met, not met, or not assessable;
3. combines applicable criteria using a documented and versioned method;
4. assigns one of the five ACMG/AMP classes;
5. optionally reports a Bayesian point total or posterior probability; and
6. preserves the evidence, provenance, limitations, and reasoning behind the
   result for human review.

This document defines why that capability is difficult, what the current
application can already provide, what is missing, and a recommended sequence
for implementing it.


2. IMPORTANT TERMINOLOGY
------------------------

ACMG/AMP classifies a sequence variant in a particular gene-disease and
inheritance context. It does not classify the gene itself.

The same variant may have different interpretations for different diseases,
inheritance modes, transcripts, or evidence available at different times.
Therefore, a classification record must be associated with at least:

- normalized variant;
- genome assembly;
- gene;
- clinically relevant transcript;
- disease or phenotype being evaluated;
- inheritance mode;
- ACMG/AMP specification and version;
- evidence sources and retrieval dates.

The five ACMG/AMP classes are:

1. Benign
2. Likely Benign
3. Variant of Uncertain Significance (VUS)
4. Likely Pathogenic
5. Pathogenic

The original 2015 ACMG/AMP framework uses evidence criteria and combination
rules. It does not inherently produce one simple numerical "ACMG score."

If a numerical result is required, the project should adopt a published,
versioned Bayesian point model. The report should still expose the individual
evidence codes and must never show only an unexplained score.


3. THE CENTRAL CHALLENGE
------------------------

The central challenge is not implementing a table of 28 ACMG/AMP criteria.
The difficult part is obtaining sufficient, reliable, disease-specific
evidence to decide whether each criterion applies and at what strength.

An automated engine must distinguish among:

- criterion met;
- criterion not met;
- criterion not applicable;
- criterion not assessable because evidence is missing;
- criterion requiring expert or manual review;
- conflicting pathogenic and benign evidence.

Treating missing evidence as negative evidence would produce unsafe and
incorrect classifications.

Rules and evidence requirements must therefore be designed together. Building
all rules first and deciding later how to obtain their inputs would lead to
criteria that cannot be evaluated correctly.


4. CURRENT APPLICATION CAPABILITIES
-----------------------------------

4.1 Ensembl VEP

Currently provides information such as:

- gene and gene identifier;
- transcript;
- molecular consequence;
- coding and protein HGVS expressions;
- canonical or MANE-related transcript information where available;
- consequence impact.

Potential ACMG/AMP relevance:

- establishes the consequence and transcript context;
- provides a starting point for PVS1, PM4, BP7, and some splice-related
  evaluations.

Limitation:

VEP consequence labels alone are not sufficient to apply these criteria.
For example, PVS1 also requires confirmation that loss of function is an
established disease mechanism, selection of a clinically relevant transcript,
and evaluation of nonsense-mediated decay and exon relevance.


4.2 MyVariant.info

Currently provides bounded population-frequency information and other
aggregated annotations.

Potential ACMG/AMP relevance:

- preliminary support for population criteria such as BA1, BS1, and PM2.

Limitations:

- the current unified evidence retains an aggregated maximum frequency rather
  than all required population-level observations;
- disease-specific frequency thresholds are not defined;
- ancestry-specific frequency, filtering allele frequency, allele count,
  allele number, homozygote count, and dataset quality filters are not
  consistently available in the retained evidence.

The current frequency value is useful for screening but is insufficient as
the sole basis for production-grade population criteria.


4.3 NCBI ClinVar

Currently provides:

- exact matching clinical records;
- clinical significance;
- review status;
- accession;
- conditions;
- evaluation date where available.

Potential ACMG/AMP relevance:

- identifies previous interpretations;
- helps locate expert-reviewed records and supporting literature;
- provides comparison and conflict information.

Limitations:

- another submitter's final classification is not automatically independent
  evidence for an ACMG/AMP criterion;
- an automated engine must avoid circular reasoning;
- assertion-level evidence, cited publications, phenotype, and submitter
  details may require deeper ClinVar record processing than the current
  bounded adapter performs;
- ClinVar assertions may conflict or may concern a different disease.


4.4 UCSC GenCC / ClinGen gene-disease evidence

Currently provides gene-disease validity claims and inheritance information
where exact claims are available.

Potential ACMG/AMP relevance:

- establishes whether the gene is credibly associated with the disease;
- helps identify inheritance mode and disease mechanism.

Limitation:

Gene-disease validity is context for variant classification, not direct proof
that a particular variant is pathogenic.


4.5 Human Phenotype Ontology (HPO)

Currently supports:

- local phenotype search and selection;
- gene and disease associations;
- simple phenotype overlap scoring.

Potential ACMG/AMP relevance:

- contributes to phenotype-specific evidence and possible PP4 evaluation.

Limitations:

- a simple HPO overlap score is not equivalent to PP4;
- PP4 requires a sufficiently specific phenotype or family history and an
  appropriate gene-disease context;
- common or nonspecific phenotypes should not trigger PP4.


4.6 Large language model

The only configured secret API key is LLM_API_KEY.

The LLM may help convert a completed, deterministic evidence record into
readable report language. It must not independently assign ACMG/AMP criteria,
points, or the final classification.


5. EVIDENCE THAT IS MISSING OR INCOMPLETE
-----------------------------------------

5.1 Variant and disease context

Required additions:

- explicit disease identifier, preferably MONDO and/or OMIM;
- inheritance mode;
- clinically relevant transcript;
- gene-specific or disease-specific ClinGen criteria specification;
- documented disease mechanism, such as loss of function or gain of function.

How to obtain it:

- ClinGen Criteria Specification Registry;
- ClinGen gene-disease validity and dosage resources;
- GenCC;
- MANE transcript data;
- curated disease selection by the user;
- optionally, licensed OMIM access.


5.2 Patient genotype

Required additions:

- heterozygous, homozygous, or hemizygous state;
- sample sex where relevant;
- affected or unaffected status;
- sequencing quality and confirmation status;
- proband and family relationships.

How to obtain it:

- FORMAT and SAMPLE columns from a patient VCF;
- pedigree data;
- explicit manual input when the source file lacks samples;
- laboratory confirmation records.

No external API key can reconstruct patient genotype or family relationships
that were not supplied with the case.


5.3 De novo evidence: PS2 and PM6

Required additions:

- whether the variant is absent from both parents;
- whether maternity and paternity were confirmed;
- phenotype consistency;
- number of independent observations.

How to obtain it:

- trio sequencing;
- validated pedigree information;
- curated case reports;
- manual evidence entry with source documentation.


5.4 Segregation evidence: PP1 and BS4

Required additions:

- affected and unaffected relatives tested;
- informative meioses;
- observed co-segregation or lack of segregation;
- penetrance and phenocopy considerations.

How to obtain it:

- pedigree and family testing data;
- published family studies;
- manual curator assessment.


5.5 Phase and allelic evidence: PM3 and BP2

Required additions:

- whether two variants are in cis or in trans;
- whether phase was directly confirmed or statistically inferred;
- pathogenicity of the second allele;
- disease inheritance model.

How to obtain it:

- parental testing;
- read-backed or molecular phasing;
- family segregation;
- curated case reports.


5.6 Population evidence: BA1, BS1, BS2, and PM2

Required additions:

- ancestry-specific allele frequency;
- filtering allele frequency or population maximum frequency;
- allele count and allele number;
- homozygote or hemizygote count;
- coverage and variant quality;
- disease prevalence, penetrance, inheritance, and allelic heterogeneity;
- gene- or disease-specific thresholds.

How to obtain it:

- gnomAD API or versioned local gnomAD datasets;
- ClinGen BA1, BS1, and PM2 recommendations;
- disease-specific VCEP specifications;
- manually documented prevalence and penetrance assumptions.


5.7 Loss-of-function evidence: PVS1

Required additions:

- established loss-of-function disease mechanism;
- transcript relevance;
- predicted nonsense-mediated decay;
- exon expression and biological relevance;
- escape from NMD;
- rescue by alternative transcripts;
- splice impact;
- location of truncation relative to known pathogenic variants.

How to obtain it:

- ClinGen PVS1 decision framework;
- VEP transcript consequences;
- MANE transcripts;
- exon and transcript annotations;
- LOFTEE or equivalent annotations;
- literature and expert review.


5.8 Functional evidence: PS3 and BS3

Required additions:

- assay type;
- validation controls;
- biological relevance;
- assay calibration;
- reproducibility;
- direction and magnitude of effect.

How to obtain it:

- peer-reviewed functional studies;
- ClinGen functional-assay guidance;
- ClinGen Evidence Repository;
- manual curation.

This evidence generally cannot be accepted safely from an unreviewed automatic
literature summary.


5.9 Computational evidence: PP3 and BP4

Required additions:

- calibrated prediction appropriate to the variant type;
- splice prediction;
- missense prediction;
- conservation where allowed by the selected specification;
- gene-specific thresholds where available;
- safeguards against double-counting correlated tools.

How to obtain it:

- VEP plugins or versioned local annotation datasets;
- calibrated tools such as SpliceAI and REVEL where appropriate;
- dbNSFP or equivalent consolidated resources;
- current ClinGen PP3/BP4 guidance.

Multiple correlated predictors must not be counted as multiple independent
pieces of evidence.


5.10 Protein domain and variant-location evidence: PM1, PS1, and PM5

Required additions:

- validated critical domains or mutational hotspots;
- exact amino-acid change comparisons;
- other established pathogenic substitutions at the same residue;
- confirmation that compared variants concern the same transcript and disease.

How to obtain it:

- ClinVar and ClinGen expert records;
- UniProt curated domains;
- gene-specific VCEP specifications;
- literature;
- exact transcript and protein normalization.


5.11 Case enrichment and published observations: PS4

Required additions:

- case and control counts;
- independent probands;
- statistical enrichment;
- avoidance of duplicate patients across publications;
- phenotype and ancestry compatibility.

How to obtain it:

- PubMed and cited literature;
- ClinGen Evidence Repository;
- locus-specific databases when reliable;
- manual curation.


5.12 Alternate explanations: BP5 and other case-level conflicts

Required additions:

- alternate molecular diagnosis;
- blended phenotype possibility;
- whether another variant fully explains the case;
- relevant environmental or acquired explanations.

How to obtain it:

- complete case review;
- broader patient test results;
- clinician and laboratory assessment.


6. API KEYS VERSUS EVIDENCE
---------------------------

More API keys are not the primary solution.

Resources that can generally be used without a new secret key include:

- Ensembl VEP;
- MyVariant.info;
- low-throughput NCBI ClinVar and PubMed E-utilities;
- gnomAD public API or downloadable data;
- ClinGen guidance and Criteria Specification Registry;
- ClinGen Evidence Repository;
- HPO data;
- MANE data;
- many locally installed prediction datasets and tools.

Potential optional credentials include:

- NCBI API key:
  increases E-utilities request throughput but does not unlock additional
  evidence;
- OMIM API key and licence:
  may provide richer disease descriptions and inheritance information;
- commercial annotation databases:
  may simplify aggregation but are not mandatory for the first implementation.

Licensing, redistribution, permitted clinical use, release version, and update
policy must be reviewed independently for every external dataset.


7. RECOMMENDED SOLUTION
-----------------------

7.1 Define a deliberately limited first scope

Recommended initial scope:

- germline variants;
- Mendelian disease;
- SNVs and small insertions/deletions;
- GRCh37 and/or GRCh38 with explicit assembly;
- one selected disease context per classification;
- no somatic, mitochondrial, pharmacogenomic, structural, or copy-number
  interpretation in the first rules engine.

Expanding scope before this subset is validated would introduce different
standards and evidence models.


7.2 Build a disease-aware evidence model

Each classification should contain:

- normalized variant identity;
- gene and transcript;
- disease identifier and name;
- inheritance mode;
- patient genotype and case context;
- selected ACMG/AMP specification and version;
- one record per evaluated criterion;
- criterion strength;
- status: met, not met, not applicable, not assessable, or manual review;
- evidence facts;
- source identifiers and URLs;
- source release and retrieval date;
- warnings and conflicts;
- final combination method;
- point total or probability if enabled;
- final five-tier class;
- reviewer and review status.


7.3 Keep evidence collection separate from rule evaluation

Recommended architecture:

Input
  -> validation and normalization
  -> disease/transcript context selection
  -> evidence collection
  -> standardized Evidence Object
  -> criterion evaluators
  -> conflict and dependency checks
  -> classification combiner
  -> human review
  -> final report

External API responses should never be passed directly into the rule combiner.
Every source must first be normalized into a stable, testable evidence field.


7.4 Make each criterion deterministic and auditable

Every criterion evaluator should return:

- criterion code;
- applied strength;
- evaluation status;
- points if the selected model uses points;
- concise rationale;
- exact evidence fields used;
- exact source records;
- specification and version;
- missing inputs;
- manual-review requirement.

The engine should not silently guess missing evidence.


7.5 Use ClinGen specifications before generic ACMG/AMP defaults

Recommended precedence:

1. Current applicable ClinGen VCEP gene/disease specification
2. Current ClinGen SVI general guidance
3. Original ACMG/AMP framework where no later specification replaces it

The selected hierarchy and all versions must appear in the classification
record.


7.6 Separate criterion evaluation from final combination

The project should support:

- evaluation of individual evidence codes;
- strength modifications;
- prevention of incompatible or double-counted evidence;
- conflict detection;
- original ACMG/AMP combination rules;
- an optional, explicitly selected Bayesian point model.

If Bayesian scoring is used, the project must document:

- point values for each evidence strength;
- pathogenic and benign thresholds;
- prior probability assumptions;
- treatment of conflicting evidence;
- overrides from gene-specific specifications;
- model version.


7.7 Preserve mandatory human review

The engine should be described as decision support, not autonomous clinical
diagnosis.

Human review should be required when:

- disease context is missing or ambiguous;
- evidence conflicts;
- a manual criterion is applied;
- a VUS is close to a threshold;
- a gene-specific specification is unavailable;
- functional or literature evidence is involved;
- the automated result disagrees with a recent expert-panel assertion;
- required provenance is incomplete.


8. PROPOSED IMPLEMENTATION ROADMAP
----------------------------------

Stage 0: Scope and standards

- approve the supported variant and disease scope;
- choose the classification combination method;
- decide whether "score" means Bayesian points, posterior probability, or
  both;
- define specification precedence and versioning.

Deliverable:

- signed-off ACMG/AMP engine specification.


Stage 1: Evidence coverage matrix

- list every supported ACMG/AMP criterion;
- define exact inputs required for each criterion;
- classify each input as automatic, manual, or mixed;
- identify its authoritative source;
- define missing-data behavior;
- mark criteria deferred from the first release.

Deliverable:

- criterion-to-evidence matrix with no implementation.


Stage 2: Classification context and input model

- add disease selection;
- add inheritance mode;
- add transcript selection;
- add genotype, zygosity, phase, de novo, and segregation fields;
- preserve patient and pedigree fields when a VCF provides them;
- define manual evidence-entry forms.

Deliverable:

- validated disease-aware case input.


Stage 3: Population and specification data

- integrate granular gnomAD evidence;
- ingest ClinGen SVI guidance metadata;
- ingest or map applicable ClinGen VCEP criteria specifications;
- version and cache external data safely.

Deliverable:

- reproducible population and specification evidence.


Stage 4: First deterministic criteria

Start with criteria whose inputs can be bounded and tested reliably, such as:

- BA1;
- BS1;
- PM2 at the currently recommended strength;
- limited consequence-based criteria only where all prerequisites are known.

Deliverable:

- criterion results without a final clinical classification.


Stage 5: Computational and loss-of-function criteria

- implement calibrated PP3/BP4;
- implement PVS1 using the ClinGen decision framework;
- add splice and transcript-specific checks;
- add double-counting safeguards.

Deliverable:

- auditable computational and loss-of-function evidence.


Stage 6: Case-level and manual evidence

- support de novo evidence;
- support segregation;
- support cis/trans evidence;
- support functional studies;
- support case enrichment and alternate diagnoses;
- require provenance and curator notes.

Deliverable:

- structured manual and mixed evidence workflow.


Stage 7: Classification and scoring

- implement the chosen combination model;
- report individual codes, strengths, points, and conflicts;
- produce the five-tier class;
- prevent classification when mandatory context is absent;
- keep VUS as a valid result rather than forcing a benign/pathogenic decision.

Deliverable:

- deterministic classification result with complete audit trail.


Stage 8: Validation

- assemble a versioned truth set from ClinGen expert-panel classifications;
- test criterion-level agreement;
- test final-class agreement;
- test conflict and missing-data behavior;
- perform blinded manual review of disagreements;
- document known limitations.

Deliverable:

- validation report and release decision.


Stage 9: Reporting

- add the deterministic ACMG/AMP result to the Evidence Object;
- allow the LLM to explain only the already-established result;
- validate that generated text cannot add unsupported criteria or change the
  classification;
- include source dates, rule versions, and limitations.

Deliverable:

- readable report that remains traceable to deterministic evidence.


9. SUGGESTED FIRST RELEASE
--------------------------

The first release should not claim to evaluate all ACMG/AMP criteria.

A safer first release would:

- require normalized variant, assembly, disease, inheritance, and transcript;
- retrieve detailed population evidence;
- select applicable ClinGen specifications;
- evaluate a small, declared subset of criteria;
- show unsupported criteria as "Not assessable";
- expose all evidence and sources;
- require manual confirmation;
- avoid a final five-tier classification until the supported subset and
  combination method have been validated.

This incremental approach permits scientific validation of each criterion
before it can influence the final result.


10. ACCEPTANCE PRINCIPLES
-------------------------

The ACMG/AMP engine should not be considered ready unless:

- classification is variant-disease specific;
- genome assembly and normalized alleles are explicit;
- transcript selection is explicit;
- every applied criterion has traceable evidence;
- missing evidence is not treated as benign evidence;
- population thresholds are disease appropriate;
- gene-specific ClinGen specifications are respected;
- correlated evidence is not double counted;
- scoring and combination logic are versioned;
- source releases and retrieval dates are stored;
- conflicting evidence is visible;
- automated and manual evidence are distinguishable;
- the LLM cannot alter criteria or classification;
- results are validated against expert-curated cases;
- a human-review state is preserved.


11. RISKS TO AVOID
------------------

- Classifying a gene instead of a variant-disease assertion
- Treating a ClinVar label as independent ACMG/AMP evidence
- Applying PP4 from a simple phenotype-overlap percentage
- Applying PVS1 from a VEP "high impact" label alone
- Applying PM2 merely because the current API returned no frequency
- Using one global allele-frequency threshold for every disease
- Counting multiple correlated prediction tools independently
- Ignoring transcript, assembly, or allele normalization
- Treating absent patient or family data as evidence against pathogenicity
- Allowing an LLM to invent publications, criteria, or scores
- Reporting an unexplained proprietary-style score
- Forcing incomplete evidence into a definitive classification
- Failing to store source and rule versions


12. FINAL CONCLUSION
--------------------

The application does not currently possess all evidence required for a
complete ACMG/AMP classification.

The missing capability cannot be solved simply by purchasing or adding more
API keys. The project needs:

- more granular public annotation data;
- disease- and gene-specific ClinGen specifications;
- structured patient and family inputs;
- curated functional and literature evidence;
- deterministic criterion evaluators;
- a documented scoring and combination model;
- conflict handling, provenance, validation, and human review.

Most foundational resources are publicly accessible without secret keys.
An NCBI key may improve request throughput, and licensed resources such as
OMIM may be useful, but neither replaces the missing clinical and family
evidence.

The recommended strategy is to build a transparent, disease-aware,
criterion-by-criterion engine in stages. The engine should return both its
result and the exact evidence path used to reach that result. A score, if
required, should be a published and versioned Bayesian score rather than an
opaque number.
